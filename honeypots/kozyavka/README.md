# HoneyForge — kozyavka, SSH Low Interaction Honeypot

Самостоятельный Cargo-пакет в `honeypots/kozyavka/`. Команды ниже выполняются
из этого каталога (`cd honeypots/kozyavka` из корня репозитория). Имя бинарника
сохранено: `honeyforge-low`. Контракт подключения к backend описан
[в документации kozyavka](../../backend/docs/kozyavka.md).

Минимальная асинхронная TCP-ловушка на Rust / Tokio. При подключении она
формирует событие, отправляет `SSH-2.0-OpenSSH_9.6\r\n` и закрывает соединение.
ОС, терминал, аутентификация и выполнение команд не эмулируются. SSH key exchange
не реализован: полноценный SSH-клиент завершит подключение с ошибкой.

## Локальный запуск

Требуется Rust 1.95+. По умолчанию сервис слушает **127.0.0.1:2222**.

```sh
cargo run --locked -- --config config/local.json
```

Конфигурация необязательна: `cargo run --locked` использует те же значения.
В другом терминале:

```sh
nc localhost 2222
```

Ожидаемый ответ: `SSH-2.0-OpenSSH_9.6`, затем закрытие соединения.
Остановить сервис можно Ctrl+C; также поддерживается SIGTERM для Docker.
Уже принятые подключения завершаются перед остановкой.

Для раздельного сбора потоков:

```sh
cargo build --locked
./target/debug/honeyforge-low --config config/local.json > events.jsonl 2> service.log
```

## Конфигурация

```json
{
  "bind_address": "127.0.0.1",
  "port": 2222,
  "banner": "SSH-2.0-OpenSSH_9.6",
  "trap_id": "9a8a8262-556b-43c4-a73f-736c32556721"
}
```

Отсутствующие поля получают значения по умолчанию. Неизвестные поля,
невалидные IP/UUID и порты вне диапазона `u16` отклоняются. `port: 0`
позволяет ОС выбрать свободный порт и используется в тестах. Баннер задаётся
без перевода строки: сервис добавляет CRLF. Допустимы 1–253 печатных ASCII-байта.

`trap_id` — постоянный UUID экземпляра ловушки, а не отдельного подключения.
В примерах задан фиксированный UUID для разработки; каждому экземпляру следует
назначить собственный UUID (например, с помощью `uuidgen`). Нулевой UUID запрещён.
Изменения конфигурации применяются после перезапуска. `RUST_LOG=debug` включает
диагностику ошибок отправки; стандартный уровень — `info`.

## Телеметрия

stdout содержит только JSON Lines: одна строка на принятое TCP-подключение.
Пример:

```json
{"schema_version":1,"event_id":"ecb66809-a21b-4527-bd14-a8ab9a7f04cf","event_type":"connection","timestamp":"2026-10-10T12:00:00.000Z","trap_id":"9a8a8262-556b-43c4-a73f-736c32556721","client_ip":"127.0.0.1","client_port":51042,"trap_port":2222}
```

`timestamp` — время принятия подключения в UTC / RFC 3339; `client_port` —
исходный порт клиента; `trap_port` — фактический локальный порт сокета.
IP и исходный порт берутся из TCP-соединения, а не из данных клиента.
За NAT, Docker port forwarding или прокси эти значения могут отражать адрес
и порт посредника. Событие фиксирует факт подключения, а не успех SSH-сессии
или доставки баннера. Ошибки записи события и диагностика идут в stderr.

### Идентификаторы и доверенная привязка к серверу

- `event_id` — UUID v4, созданный один раз при принятии конкретного подключения.
  Новое подключение получает новый ID, даже если его адреса и порты совпадают
  с предыдущим. Клонирование и повторная сериализация сохраняют ID.
- `trap_id` — постоянный идентификатор ловушки; у разных событий одной ловушки
  он одинаковый.
- `server_id` — идентификатор сервера, к которому относится ловушка. Он отсутствует
  в исходном JSON ловушки и не принимается её конфигурацией. Привязку устанавливает
  агент/backend по проверенной регистрации и учётным данным.

Контракт будущей интеграции: backend определяет пользователя и разрешённый
`server_id` из аутентифицированного контекста агента, затем проверяет принадлежность
`trap_id` этому серверу. Если учётные данные дают доступ к нескольким серверам,
выбранный сервер проверяется по зарегистрированной привязке агента. Любой
`server_id`, переданный в сообщении, сам по себе не подтверждает принадлежность;
несовпадение с проверенным контекстом отклоняется. Поле `trap_id` также не является
доказательством прав доступа.

После проверки центр связывает событие с доверенным `server_id`. Ключ
дедупликации: `(server_id, event_id)` в контексте авторизованного пользователя.
Повтор с тем же ключом не создаёт новое событие; изменённое содержимое под тем же
ключом должно отклоняться как конфликт. Этот контракт описывает будущий приём
событий, а не реализованную здесь аутентификацию или дедупликацию.

Будущий агент должен сохранять исходное событие вместе с `event_id` в своей
устойчивой очереди до отправки. При повторной отправке и восстановлении после
перезапуска используется сохранённый ID; вызывать `ConnectionEvent::new` для
повтора нельзя. Сейчас реализованы генерация и сохранение ID при сериализации;
HFSP, очередь повторной доставки и серверный backend пока не реализованы.

## Архитектура и интеграция с агентом

- `src/config.rs` — чтение и валидация JSON-конфигурации.
- `src/network.rs` — приём TCP, параллельные задачи, отправка баннера и остановка.
- `src/telemetry.rs` — структура события, сериализация JSONL и интерфейс `EventSink`.
- `src/main.rs` — конфигурация, tracing, сокет и обработчики сигналов.

Библиотечная функция `network::serve` принимает готовый `TcpListener`, конфигурацию,
`Arc<dyn EventSink>` и future остановки. Будущий Rust-агент может реализовать
`EventSink`, передавая события в свою очередь, без изменения сетевой логики.
Синхронный sink должен быстро возвращать результат. Текущий `StdoutSink` блокирует
stdout на время записи целой строки и выполняет flush; медленный сборщик может
создавать обратное давление. Локального буфера с гарантированной доставкой нет.

Одновременно выполняется не более 128 обработчиков; дальнейшие подключения ждут
в очереди ОС. Таймаут отправки баннера — 3 секунды. Входящие данные не читаются,
команды не обрабатываются. HFSP, Hysteria 2, PostgreSQL и ClickHouse не реализованы.

## Docker

```sh
docker compose up --build -d
nc localhost 2222
docker compose logs honeypot
docker compose down
```

Compose публикует порт **только на 127.0.0.1:2222 хоста**. Внутри контейнера
`config/docker.json` использует `0.0.0.0:2222`, чтобы Docker мог перенаправлять
подключения. Конфигурация смонтирована read-only; процесс работает без root,
с read-only файловой системой и без Linux capabilities. Образ собирается
в два этапа с `Cargo.lock`. Docker logs показывает оба потока; агенту нужен stdout
контейнера для JSONL. При изменении порта в docker.json обновите также целевой
порт в `compose.yaml`. Локальный сервис и контейнер не могут одновременно
занимать один порт 2222.

## Проверки

```sh
cargo fmt --all --check
cargo check --locked
cargo test --locked
docker compose config --quiet
```

Тесты проверяют TCP-подключение, точный баннер с CRLF и закрытие соединения,
пользовательский баннер, 32 параллельных клиента, соответствие адресов и портов,
UUID, уникальность `event_id` и его сохранение при повторной сериализации,
JSONL и UTC-время, запрет `server_id` в конфигурации и остановку listener.
Сетевые тесты используют свободные loopback-порты, не занимая 2222.
Все команды предназначены для локального запуска; обращения к Ubuntu-серверу
не требуются.
