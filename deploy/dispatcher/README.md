# HoneyForge TCP Dispatcher

Пользователь указывает только порт ловушки. Режим выбирает Control Plane автоматически:

1. Первая и единственная TCP-ловушка на порту, например 2222: Docker публикует 0.0.0.0:2222 напрямую.
2. Вторая ловушка выбрала 2222: Control Plane переводит обе ловушки на уникальные loopback-порты, например 127.0.0.1:31001 и 127.0.0.1:31002, запускает Dispatcher на 0.0.0.0:2222 и передаёт ему обе цели с весами.
3. Ловушка на другом порту, например 8080: остаётся прямой. Возможность разных портов не меняется.
4. Если в группе останется одна ловушка, Control Plane может свернуть Dispatcher и снова опубликовать её напрямую. Это отдельная reconcile-операция.

attacker:2222 -> hf-dispatcher:2222 -> 127.0.0.1:31001 Low 50%
                                     -> 127.0.0.1:31002 Cowrie 30%
                                     -> 127.0.0.1:31003 High 20%

Выбор: SipHash(static_key, source_ip) % 100. Source TCP port не учитывается, поэтому повторное подключение одного IP попадает в ту же ловушку, пока не меняется IP или конфигурация.

## Контракт Control Plane

Control Plane строит проверенный JSON вида example.json, атомарно заменяет /etc/honeyforge/dispatcher.json через write-temp + rename. Диспетчер не является open proxy: цели разрешены только на loopback-адресах, веса должны быть положительными и в сумме давать 100.

Изменение весов и целей на уже слушаемом порту применяется без обрыва действующих TCP-соединений. Добавление или удаление публичного порта требует controlled restart/reconcile диспетчера.

Запуск: cargo run -p hf-dispatcher -- --config deploy/dispatcher/example.json

Следующая связка с агентом: Control Plane генерирует этот конфиг из групп трапов по host_port, отправляет агенту команды перепубликовать Docker-порты в loopback и обновить Dispatcher через HFSP.
