# Low/Middle: граф и реакция на нарушение изоляции

High VM и её сценарии запуска не изменены. Изменения в этих компонентах требуют
сборки `hf-agent`, `hf-center` и отдельного `backend`; образы Low/Middle для этих
изменений пересобирать не требуется. Уже установленный агент нужно обновить
на его VPS — замена артефакта на Center обновляет только последующие установки.

## Что различает система

- `simulated`: команды и виртуальные файловые операции Middle. Сборщик
  назначает источник сам и привязывает событие к каталогу ловушки. Поля JSONL
  не могут объявить событие отчётом монитора хоста.
- `host_observer`: события от наблюдателя агента, переданные через отдельный
  доверенный endpoint Center. PID связывается с boot ID и временем рождения
  процесса. Другой процесс с повторно использованным PID не продолжает граф.
- `unverified`: прочие источники. Похожая команда не доказывает побег.

Для подтверждения нужны две выборки одного процесса, полное совпадение
container ID в cgroup, host PID **и** mount namespaces процесса при сохранённой
изоляции init контейнера. Один и тот же формат доказательства v2 проверяют
агент, аварийная реакция, Center и нормализатор графа. High в него не входит.
Это валидация отчёта авторизованного наблюдателя, а не независимая аттестация
хоста: агент, уже скомпрометированный с root-правами, может лгать.

Граф загружает до 128 подходящих узлов, хранит до 128 совпавших узлов и
64 event ID в одном состоянии, окно продолжения — 30 минут. Повторы не
повышают покрытие. Позднее событие сохраняется, но не создаёт обратную временную
связь. Подтверждённое доказательство сохраняется независимо от окна.
`similarity` — доля совпавших узлов, не вероятность атаки. Ответ API содержит
`session_key` и `evidence_domain`. Новые варианты остаются предложениями для
ручной проверки. Администратор просматривает `GET /api/v1/knowledge/proposals`
и принимает или отклоняет предложение через
`POST /api/v1/knowledge/proposals/{id}/review` с телом
`{"decision":"accept","technique_id":"...","predecessor_node_id":"..."}`
или `{"decision":"reject"}`. Предшественник необязателен; если указан,
он должен принадлежать выбранной технике. Принятый узел имеет только уровень
`attempt`. Автор и время решения сохраняются в PostgreSQL.
Автоматического признания нового варианта доказательством побега нет.

## Обновление и конфигурация

1. Собрать и протестировать исходники командами ниже.
2. Сгенерировать разные `TELEMETRY_INGEST_TOKEN` и `CENTER_INGEST_TOKEN`.
   Последний должен совпадать с `HF_CENTER_POSTGRES_TELEMETRY_TOKEN` у Center.
   `deploy/vps/configure.py` создаёт и сохраняет отдельный `center_graph_token`.
   Не выдавать этот секрет ловушкам. ClickHouse-only installer граф не включает.
3. С новым backend и его окружением выполнить `honeyforge-backend migrate`
   перед запуском новой версии. Миграция `202610120002` удаляет только старое
   производное состояние `attack_graph_progress` с небезопасными областями
   сопоставления. Исходные события, знания и ClickHouse не удаляются. Простой
   перезапуск backend миграции не выполняет.
4. Обновить backend и Center, затем `hf-agent` на тестовой VPS. Проверить
   доставку новых Low/Middle событий и результаты графа.

Миграции `202610120004` и `202610120005` добавляют сопоставление класса
процесса, стартовые техники доступа к runtime socket и исходящего подключения,
а также поля ручной проверки предложений. Сначала нужно выполнить миграции,
затем запускать новый backend.

Для Low/Middle агент сопоставляет наблюдаемое действие с уровнем ловушки,
субъектом (процесс, PID, boot ID, cgroup и namespaces), операцией, ресурсом,
результатом и контекстом контейнера. eBPF tracepoints фиксируют exec, результат
`openat` и `openat2` для точного набора чувствительных путей и результат `connect` вместе
с IPv4/IPv6 адресом и портом назначения. Адрес сохраняется как evidence графа;
класс ресурса остаётся обобщённым для сопоставления вариантов. Неуспешное открытие Docker socket вызывает тревогу;
успешное открытие или критическое нарушение Docker-конфигурации запускает
карантин **одной** ловушки. Агент сохраняет маркер, отсоединяет её маршрут от
Dispatcher и останавливает Compose-проект, закрывая его соединения. После
рестарта он повторно применяет маркер. Center получает отдельный результат,
сохраняет статус `applied` или `failed` и запрещает повторное развёртывание
по тому же trap ID. Ошибку видно через `GET /v1/traps/isolated`.
Подтверждённый выход остаётся отдельным основанием для реакции на весь VDS.

UDP-приёмник Center ограничивает трафик до разбора пакета и затем отдельно
по каждому авторизованному агенту. Hysteria auth endpoint ограничивает размер
тела и частоту проверки учётных данных. Перегрузку самого публичного QUIC
сервера это не исключает: её нужно ограничивать на сетевом уровне.

Реакция имеет три уровня: обычные подозрительные сигналы дают тревогу и
сохраняют наблюдение; подтверждённое локальное решение об изоляции Low/Middle
останавливает только Compose-проект этой ловушки, а Center блокирует её повторное
развёртывание; только подтверждение выхода в host PID и mount namespaces
отзывает credentials агента, закрывает его Hysteria-сессию и помечает VPS
скомпрометированным. Сопоставление графа само по себе не повышает уровень реакции.
Это правило намеренно не считает виртуальные команды Middle доказательством
доступа к хосту. Накопительный риск-score по нескольким графовым сигналам пока
не реализован; реакция опирается на проверенную форму конкретного события.

Теперь Center перед командой Low/Middle регистрирует сервер и ловушку в обычных
`servers`/`traps` backend через локальный API и связывает их с agent ID.
Middle получает канонический server ID от backend; поле не требуется вводить
вручную в веб-интерфейсе. Если backend недоступен, Center не ставит новую ловушку. Center
проверяет привязку событий до ACK: неизвестные пары `agent_id`/`trap_id`
сохраняются в `events.rejected.jsonl` рядом с основным spool. Backend также
проверяет эту пару при индексации; HTTP 404/409/422 сохраняются в
`*.postgres-graph-rejected.jsonl` с исходным offset. Оба журнала нужны для
диагностики, но сами по себе не добавляют событие в граф. Уже установленные
до этого изменения ловушки нужно явно сверить и зарегистрировать через раздел
«Существующая ловушка» веб-интерфейса после обновления Center. До этого их новые
события попадают только в карантин, а не в ClickHouse/граф: старые привязки
не появляются автоматически. Для сверки нужны agent ID, trap ID, уровень и
внешний порт из проекта ловушки на соответствующей VPS.
После подтверждения команды удаления Center помечает запись backend как
`removed`, освобождает резерв порта и убирает локальную привязку. Обновление
backend подтверждается до ACK агенту: при временной ошибке Agent повторит ACK
из SQLite, а Center сохранит ожидаемое удаление после перезапуска.

ClickHouse и PostgreSQL
имеют отдельные подтверждения и курсоры; успех одного не доказывает успех другого.
401/403/5xx и неверный ACK оставляют курсор графа для повторной попытки;
404/409/422 сохраняются в журнал отказов до продвижения курсора.

## Локальные проверки без выключения сервера

Из корня репозитория:

```sh
python3 deploy/vps/test_emergency.py
python3 deploy/vps/test_configure_revocation.py
cargo test --locked -p hf-core -p hf-services -p hf-agent -p hf-center
cargo test --locked --manifest-path backend/Cargo.toml
```

`test_emergency.py` подменяет Docker, nft, systemctl, sync, logger и stat.
Он проверяет отказ без armed-флага и при symlink-маркере, порядок остановки
ловушки/изоляции/выключения, продолжение poweroff при отказе nft и ненулевой
выход для повтора службы при отказе poweroff. Реальные службы не запускаются.
Rust-тесты проверяют границу доверия JSONL, точное сопоставление cgroup,
формат доказательства, исключение High, namespace mismatch, ограничения
политики, приоритет очереди после перезапуска, ACK зеркала и лимит приёма.

Для проверки перед установкой на **отдельной тестовой VPS**, с
`HF_EMERGENCY_ARMED` выключенным: выключите Center,
создайте тестовую тревогу, перезапустите Agent и убедитесь, что её UUID остаётся
в SQLite outbox. После запуска Center проверьте ровно один экземпляр UUID в
spool и ClickHouse, затем отсутствие тревоги в outbox после ACK. Отдельно
выполните в Middle `sudo id`, `id`, `cat /etc/shadow`: это виртуальные команды,
их домен должен быть `simulated`, статус не `confirmed`. Проверьте смену boot ID
и повтор PID разными `start_ticks` в тестах графа. Отзыв проверяйте по
`transport_disconnected=true`, отсутствию agent ID в Hysteria Traffic Stats
`/online`, отказу новой авторизации и отсутствию принимаемых Kazik сообщений.
Не запускайте аварийное выключение на рабочей VPS.

Для проверки SQL используйте **отдельную** БД `honeyforge_test` и существующий
`backend/scripts/test_postgres.py`. Проверьте дополнительные сценарии:

- одно событие дважды: одно normalized action и неизменное покрытие;
- одинаковые PID с разными start_ticks: разные состояния;
- виртуальная команда Middle: `simulated`, никогда `confirmed`;
- обычный telemetry token на Center endpoint: 401;
- события разных агентов: независимые состояния;
- неизвестная ловушка: запись в журнале отказов, отсутствие ложного успеха;
- отказ PostgreSQL: курсор не продвигается, после восстановления повтор идемпотентен.

## Проверка реакции на отдельной тестовой VPS

Сначала оставьте `HF_EMERGENCY_ARMED` выключенным. Подтверждённый инцидент всё
равно блокирует команды и отзывает агент в Center; поэтому используйте отдельную
тестовую регистрацию. Проверяйте сохранение denylist после рестарта Center,
отказ дальнейшей телеметрии/команд/регистрации и закрытие Hysteria-сессии.
Отключите доступность Stats API в тестовой среде и убедитесь, что после её
восстановления повторное закрытие срабатывает. Ретрай также повторяет запись
отзыва credentials, если она ранее не удалась.

Аварийная служба с `HF_EMERGENCY_ARMED=1` действительно изолирует и выключает
VPS. Для испытания этого этапа нужны отдельная машина и консоль провайдера.
Не запускайте её на рабочем Center. Тревога получает приоритет в SQLite;
локальная реакция не отменяется из-за ошибки постановки сообщения в очередь.
Агент повторяет постановку и после перезапуска восстанавливает тревогу из
root-owned файла инцидента с прежним message ID. После ACK он сначала сохраняет
отметку подтверждения, затем удаляет запись SQLite, поэтому прерванное удаление
завершится при следующем запуске без повторного создания тревоги.
Center отправляет ACK только после сохранения события/denylist, затем закрывает
транспорт; недоступность Stats API не блокирует приём остальных агентов.

## Оставшиеся границы

Монитор использует eBPF tracepoints через bpftrace и периодические proc-снимки.
Он перехватывает только перечисленные точные пути через `openat` и `openat2`; относительные,
символические и другие файловые операции, `read`/`write`, bind/listen
и другие сетевые операции этим датчиком не покрыты. Он может пропустить
короткоживущие процессы и не подтверждает побег, полностью утративший известный
cgroup. Переполнение бюджета и отсутствие наблюдателя означают ухудшение
покрытия, а не безопасность хоста. Изменения capabilities/mounts/namespace
проверяются аудитом; исходящая сеть контейнеров пока не закрыта allowlist-ом.
Root внутри Middle не равен побегу; подозрение само по себе не запускает poweroff.
